# BC 28.3 `/csh` WebSocket upgrade returns 403 — RESOLVED

**Date opened:** 2026-07-24
**Date resolved:** 2026-07-25
**Status:** RESOLVED. Root cause was a **missing `Origin` request header** on the WebSocket
upgrade, which BC 28.3's new WebSocket origin-validation middleware rejects. Fixed by sending
`Origin: <scheme>://<host>[:port]` derived from the base URL. Both `cronus28` (28.3) and
`cronus281` (28.0) are green.
**Owner:** done.

## One-line summary

The client authenticates fine against `cronus28`, but the `/csh` WebSocket **upgrade** was rejected
with a bare `403 Forbidden` (empty body). The identical code connected successfully to `cronus281`
(BC 28.0). The cause: BC 28.3's web server enforces **WebSocket Origin validation**; our `ws` client
sent no `Origin` header, so the server's `RequestOriginValidationMiddleware` denied the upgrade with
a 403. BC 28.0 did not enforce this.

## Root cause (verified from decompiled 28.3 source + live wire)

The web server (`Prod.Client.WebCoreApp.dll`, the ASP.NET Core front that serves `http://.../BC` and
proxies to the NST) runs `RequestOriginValidationMiddleware` on every request. For a WebSocket
upgrade it does:

```csharp
// Prod.Client.WebCoreApp/Middleware/RequestOriginValidationMiddleware.cs:95
if (!webSocketOriginValidationDisabled && IsWebSocketUpgrade(context)
        && !IsOriginAllowedForWebSocket(originHeader, context.Request)) {
    context.Response.Clear();
    context.Response.StatusCode = 403;      // <-- our bare 403, empty body, pre-app
    await context.Response.WriteAsync("");
    return;
}
```

```csharp
private bool IsOriginAllowedForWebSocket(string origin, HttpRequest request) {
    if (string.IsNullOrEmpty(origin)) return false;          // <-- we sent no Origin -> false -> 403
    if (allowedWebSocketOrigins.Contains(NormalizeOrigin(origin))) return true;
    return IsSameOrigin(origin, request);                    // host + scheme + port must all match
}
```

`webSocketOriginValidationDisabled` comes from `AspCoreNavWebConfig.DisableWebSocketOriginValidation`,
which **defaults to `false`** (validation ON). Our client used the `ws` npm library, which does **not**
send an `Origin` header unless told to, so `origin` was empty → `IsOriginAllowedForWebSocket` returned
`false` → 403. BC 28.0 did not gate the upgrade on origin, so the same header-less upgrade succeeded.

### Why the earlier "antiforgery / csrftoken" hypothesis was wrong

The decompiled 28.3 antiforgery gate (`QueryBasedAntiforgeryProtectionMiddleware`) returns **401**, not
403, on a bad token — and the `/csh` upgrade we sent (cookie value as `csrftoken`) passed it. The
observed status was **403**, which only `RequestOriginValidationMiddleware` produces. The 401→403
progression seen while probing is: no-auth → 401 from the authentication challenge (before origin
validation); with-auth → passes auth → origin middleware → empty Origin → 403. Antiforgery was never
the blocker.

## The fix

`src/connection/connection-factory.ts` (`create()`), one line after assembling the upgrade headers:

```ts
headers['Origin'] = new URL(this.bcConfig.baseUrl).origin;  // scheme+host+port, no path
```

`URL(...).origin` yields exactly what `IsSameOrigin` checks (host, scheme, port; default ports
omitted, non-default ports kept), so a same-origin upgrade is always allowed. It is a no-op against
28.0, which does not inspect the header. `getWebSocketHeaders()` was deliberately left untouched so
the HTTP report-download path (which reuses it) does not gain a spurious Origin.

## Evidence


The committed `tests/integration/connection.test.ts` fails on `cronus28` with the same 403

## The decisive detail

- The **plain GET** 400 comes back as BC's app-level HTML error page → the request reached the app.
- The **authenticated upgrade** 403 is `content-length: 0`, no body, no diagnostic headers → it is
  rejected **before** BC's app handler, at a middleware / antiforgery / reverse-proxy layer.

401-without-auth then 403-with-auth means: identity is accepted, then the upgrade is forbidden. That
is the shape of an **antiforgery/CSRF mismatch** or a **proxy/host policy** that 28.3 tightened, not
a credentials problem.

## What we tried

1. Fresh authentication each run — cookie + csrftoken always obtained. Not an auth failure.
2. `BC_CLIENT_VERSION=27.0.0.0` / `BC_SERVER_MAJOR=27` — still 403. Not the version string in the
   OpenSession payload (the upgrade fails before any OpenSession is sent anyway).
3. Plain GET vs WS upgrade, with and without auth — isolated the failure to the authenticated
   upgrade specifically (table above).
4. Captured the 403 upgrade response — empty body, no reason header.
5. Confirmed `cronus281` (BC 28.0) works end-to-end with the same code, so the client is correct
   for at least one 28.x server.

## Ruled out

- Server down (SignIn/root respond).
- Auth/credentials (cookie + csrf obtained; 401→403 progression).
- Client version string in the invoke payload (upgrade fails earlier; and 27 was tried).
- A code regression in this repo (same code works against `cronus281`).

## Hypotheses, ranked

1. **Stale antiforgery key after a container/NST restart.** The csrftoken is minted by the SignIn
   flow; if 28.3's NST rotated its data-protection/antiforgery key and the SignIn cookie and the
   `csrftoken` query value are validated against different key material, the upgrade 403s.
   → *Cheapest test: restart the cronus28 container / BC Server Instance and retry. If it clears,
   this was it.*
2. **28.3 changed the `/csh` handshake contract.** A newer build may require the csrftoken in a
   **header** instead of (or in addition to) the query string, a different query parameter, or a
   `Sec-WebSocket-Protocol` value the client does not send. `getWebSocketQueryParams()` returns only
   `{ csrftoken }` and `getWebSocketHeaders()` returns only `{ Cookie }`
   (`src/connection/auth/ntlm-provider.ts:140-146`).
   → *Decisive test: capture a real browser handshake against cronus28 and diff it against ours.*
3. **Reverse proxy / host in front of 28.3 blocks WS upgrades** (IIS ARR without WebSocket enabled,
   or an antiforgery filter on the proxy). The bare 403 with no BC error page fits a proxy-layer
   rejection.
   → *Test: hit the NST's own port directly, bypassing whatever serves port 80, and/or check the
   proxy/site config for WebSocket support.*
4. **28.3 requires a protocol/compat-version handshake the client omits.** Less likely (upgrade
   fails before protocol negotiation), but check the client-config endpoint (below) for a version
   the server now enforces.
